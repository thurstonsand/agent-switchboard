# Pi lifecycle signals

## Answers

### Activity: `agent_start` → Working; attention spans → Blocked; `agent_settled` → Idle

Persist `turn_in_progress = true` and Activity = Working synchronously in `agent_start`. Do **not** make `agent_end` Idle: one logical run may execute `agent.prompt()`, automatic retry/compaction or queued-message `agent.continue()` calls, and more low-level agent start/end cycles before settlement. Pi emits `agent_settled` only after that loop has no continuation left, and defines it as having no automatic retry, compaction, or queued continuation remaining. Persist `turn_in_progress = false`, Activity = Idle, and the completion timestamp synchronously in `agent_settled` ([agent-session.ts:1752-1776](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/agent-session.ts), [types.ts:912-918, 985-988](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/extensions/types.ts)).

Pi sets its run-active flag false before awaiting extension `agent_settled` handlers. Calls which try to start another prompt from inside settlement are deferred until all settlement handlers finish, after which they produce a separate run. Thus an Idle write in `agent_settled` cannot race a continuation from the run that just settled; a separately triggered prompt may legitimately change it back to Working immediately afterward ([agent-session.ts:1044-1066](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/agent-session.ts)).

Blocked is an overlay on the active turn. Maintain a set of outstanding attention IDs: request adds an ID and makes Activity Blocked; resolve removes it and restores Working only when the set becomes empty. The permission gate emits request before waiting and resolve in `finally`; the interview adapter emits request at `tool_call` and resolve at `tool_execution_end` ([pi-permissions/extensions/hooks.ts:128-166](/Users/tsandberg/.pi/agent/git/github.com/thurstonsand/pi-permissions/extensions/hooks.ts), [interview-attention.ts:3-15](/Users/tsandberg/code/personal/ansiblonomicon/bootstrap/capabilities/agent-harness/configuration/assets/pi/extensions/interview-attention.ts)). The existing companion already implements the required set rather than a lossy boolean ([attention.ts:32-60](/Users/tsandberg/code/personal/ansiblonomicon/bootstrap/capabilities/agent-harness/configuration/assets/pi/extensions/glimpse-companion/companion/attention.ts)). Clear the set on `agent_settled`, session replacement, and reload as reconciliation against a missed resolve.

Pi v0.99.2 also exposes generic `ui_prompt_start`/`ui_prompt_end`, but those wrap every `ctx.ui` select/confirm/input/editor/custom prompt and are queued as microtasks. They are broader than the product definition of Blocked and do not cover the browser-based interview by themselves, so the namespaced permission/interview protocol remains the authoritative signal ([runner.ts:569-613](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/extensions/runner.ts), [types.ts:992-1005](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/extensions/types.ts)).

### Interrupted versus Dormant: persist the turn boundary, not the exit kind

The durable discriminator is the last committed `turn_in_progress` bit (or equivalent phase), independent of liveness:

- `session_start`: mark the new process lease Live; for an existing tracked row, reconcile the freshly launched, non-continuing Pi process to `turn_in_progress = false` and Idle until an `agent_start` arrives. Do not create a never-used new session's roster row here. Session initialization emits `session_start` without starting an agent run ([agent-session.ts:3206-3209](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/agent-session.ts)).
- `agent_start`: synchronously commit `turn_in_progress = true` and Working before returning.
- attention request/resolve: synchronously commit Blocked/Working without changing `turn_in_progress`.
- `agent_settled`: synchronously commit `turn_in_progress = false`, Idle, completion time, and the final cached excerpt before returning.
- `session_shutdown`: mark the process lease no longer live, but **never clear** `turn_in_progress` merely because shutdown ran.

When the boot/process lease is dead, `turn_in_progress = true` means Interrupted; false means ordinary Dormant. The existing recorder's per-boot UUID plus PID is suitable liveness evidence: on macOS it reads `kern.bootsessionuuid` ([shared/session-recovery/core.ts:35, 58-73](/Users/tsandberg/code/personal/ansiblonomicon/bootstrap/capabilities/agent-harness/configuration/assets/shared/session-recovery/core.ts)). A later schema ticket may choose the exact lease fields.

This handles graceful signals, uncaught crashes, SIGKILL, and power loss uniformly. SIGTERM/SIGHUP call the normal runtime disposal path, whose shutdown reason is still `quit`; uncaught exceptions exit without emitting `session_shutdown`; power loss emits nothing ([interactive-mode.ts:4167-4200, 4228-4249, 4260-4276](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/modes/interactive/interactive-mode.ts), [agent-session-runtime.ts:404-409](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/agent-session-runtime.ts)). In-process `new`/`resume`/`fork` first await `abort()`, which settles the outgoing run, and only then emit shutdown, so an intentional replacement leaves the old session Dormant rather than Interrupted ([agent-session-runtime.ts:167-177](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/agent-session-runtime.ts)).

Use synchronous `node:sqlite` statements inside the awaited Pi lifecycle handlers, with each boundary as one transaction. Configure WAL with `PRAGMA synchronous=FULL`: SQLite says WAL+NORMAL can lose a committed transaction after power loss, while FULL adds a WAL sync after each commit for power-loss durability ([SQLite `synchronous`](https://www.sqlite.org/pragma.html#pragma_synchronous)). Keep the DB, `-wal`, and `-shm` together; SQLite defines the WAL as part of persistent database state ([SQLite WAL §3](https://www.sqlite.org/wal.html#the_wal_file)).

There is one failure limitation: Pi awaits lifecycle handlers, but catches their exceptions and reports an extension error rather than aborting the run ([runner.ts:1079-1103](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/extensions/runner.ts)). The in-process event bus is weaker still: `emit()` does not await its async wrapper ([event-bus.ts:12-27](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/event-bus.ts)). Attention listeners must therefore be synchronous (no `await` before the commit). A DB write failure can otherwise leave stale durable state while Pi continues; implementation should treat recorder write failure as fatal or visibly fail closed. Exactly how to terminate belongs in implementation design, but silently logging is insufficient for guaranteed classification.

### Location: ask the current tmux server, then compare its socket basename

`$TMUX` proves only that the process is inside tmux; its first comma-separated field is the socket path. Prefer one command against the inherited server:

```sh
tmux display-message -p '#{socket_path}\t#{session_name}\t#{window_name}\t#{pane_id}\t#{pane_title}'
```

A managed process requires `#{socket_path}` to equal the socket created by `tmux -L sessions` (normally basename `sessions`), and records the returned session/window/pane names and IDs. Do not infer management from a session-name convention. A throwaway tmux 3.7c experiment on the work Mac returned `/private/tmp/tmux-501/sessions`, `research`, `lifecycle`, and `%0` for a `tmux -L sessions ... new-session -s research -n lifecycle`; the current research pane on the default server returned `/private/tmp/tmux-501/default`. `TMUX_PANE` can cross-check the pane ID.

Run this once at recorder startup and fail closed (outside Sessions) if the command fails or the socket is not `sessions`. The existing pi-sessions helper likewise treats `$TMUX` only as an inside-tmux boolean and obtains window identity from tmux formats/options ([pi-sessions/extensions/shared/tmux.ts:25-27, 40-56](/Users/tsandberg/code/personal/pi-sessions/extensions/shared/tmux.ts)).

### Session identity changes: replacement is two ordered records

The event reason sets are exact: start is `startup | reload | new | resume | fork`; shutdown is `quit | reload | new | resume | fork` ([types.ts:721-727, 790-795](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/extensions/types.ts)). Initial process launch always defaults to `startup`, even when CLI startup opened an existing session; `resume` means an in-process switch, not “this process was launched with an old transcript” ([agent-session.ts:475, 3206-3209](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/agent-session.ts)). `reload` shuts down and rebuilds the extension runner around the same session ID ([agent-session.ts:3590-3619](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/agent-session.ts)).

For `/new`, `/resume`, and `/fork`, Pi emits shutdown against the old context first, then constructs the replacement and emits start against its new context; shutdown carries `targetSessionFile`, and start carries `previousSessionFile` ([agent-session-runtime.ts:196-251, 262-345](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/agent-session-runtime.ts)). The recorder should synchronously mark the old ID Dormant without deleting it, retain the same managed pane identity, then bind/upsert the new ID when its first turn begins. It must also replace the pane/window's explicit session-ID option so the Dispatcher opens the new conversation, rather than leaving the launch-time ID stamped forever. A no-turn `/new` has changed the pane's prospective ID but does not yet create a roster Session, because the vocabulary begins tracking at the first turn.

`--session-id` is the correct lazy-revival primitive: Pi opens the exact project ID when found and creates a new session with that ID otherwise ([main.ts:436-448](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/main.ts), [args.ts:299](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/cli/args.ts)).

### Subagent exclusion: use the child-local durable bootstrap identity

Do not use tmux socket, session name, window name, cwd, or process environment. pi-sessions stamps a `pi-sessions.handoff-bootstrap` custom entry into the child before launch; the `launch: "subagent"` variant requires `{childSessionId, ownerSessionId, depth, requestResponse}` ([metadata.ts:13, 21-28, 45-59](/Users/tsandberg/code/personal/pi-sessions/extensions/session-handoff/metadata.ts)). Preparation explicitly flushes that bootstrap to the child session file before starting Pi ([spawn.ts:31-45, 69-78](/Users/tsandberg/code/personal/pi-sessions/extensions/session-handoff/spawn.ts)).

Use pi-sessions' owning predicate: fold the active branch with `findCurrentHandoffBootstrap()`, require `launch === "subagent"`, and require both bootstrap session IDs to equal `ctx.sessionManager.getSessionId()` ([metadata.ts:210-264](/Users/tsandberg/code/personal/pi-sessions/extensions/session-handoff/metadata.ts), [subagents/settle.ts:155-168](/Users/tsandberg/code/personal/pi-sessions/extensions/subagents/settle.ts)). This remains valid after kickoff/consumption and across resume; an environment variable would not. The Sessions recorder should ideally consume an exported pi-sessions predicate/schema rather than duplicate it, but the durable custom entry is the compatibility boundary.

### Excerpts: cache message events; never scan JSONL

`message_end` supplies the complete `AgentMessage`. Cache the most recent user text immediately and cache each assistant text in memory; on `agent_settled`, write the last cached assistant as the completed reply. Pi dispatches `message_end` to extensions and then synchronously appends that same message to the SessionManager, so this follows transcript semantics without reading the JSONL ([types.ts:1038-1041](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/extensions/types.ts), [agent-session.ts:1109-1132, 1280-1296](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/agent-session.ts)). Limit text size before writing.

A crash mid-stream leaves the preceding completed assistant excerpt, which is preferable to presenting a partial reply as complete. If the preview later wants partial streaming text, that is a separate `message_update` product decision. `ctx.sessionManager.getBranch()` is appropriate for the one-time subagent identity fold, but not for excerpts; it walks the branch and allocates an array ([session-manager.ts:1462-1478](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/session-manager.ts)).

### Unarchive: the first user `message_start`, not `agent_start`

Unarchive synchronously when `message_start` has `message.role === "user"`. That event covers ordinary prompts and queued steer/follow-up user messages. `agent_start` is unsuitable because Pi may emit it again for retry/compaction/queued continuation within the same logical run; `turn_start` likewise marks every provider turn, including tool continuations. `before_agent_start` exposes useful raw prompt text but occurs only on the direct `prompt()` path, whereas queued input has its own path ([agent-session.ts:1921-2037, 2076-2145](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/agent-session.ts)). Pi's message event conversion preserves the message role for the recorder ([agent-session.ts:1262-1296](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/agent-session.ts)). This lifecycle action is not a Visit.

### Existing guards and signal hack

- **Remove `viaSignal`.** Under v0.99.2 the late `prependListener()` still runs before Pi's earlier registered signal handler, so it distinguishes graceful SIGHUP/SIGTERM from interactive quit, but it cannot cover uncaught crash, SIGKILL, or power loss and depends on private handler ordering. More importantly, Sessions v2 never deletes a row on quit: durable `turn_in_progress` already decides Interrupted versus Dormant. The current coupling is visible at [session-recovery/index.ts:10-34, 77-99](/Users/tsandberg/code/personal/ansiblonomicon/bootstrap/capabilities/agent-harness/configuration/assets/pi/extensions/session-recovery/index.ts); Pi registers its handlers before extension initialization at [interactive-mode.ts:907-962](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/modes/interactive/interactive-mode.ts).
- **Remove `ctx.hasUI` as a tracking guard.** Pi defines it as dialog-capable UI and says it is true in TUI **and RPC** modes; it neither proves that the session is managed nor that it is persistent ([types.ts:325-334](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/extensions/types.ts)). The `tmux -L sessions` socket check is the management boundary.
- **Keep `getSessionFile()` as a persistence invariant, not a first-turn signal.** `undefined` identifies an in-memory/`--no-session` context which cannot be revived. A non-undefined path may precede the actual file: Pi creates the file only once a user or assistant message exists, then uses synchronous `openSync`/`writeFileSync` ([session-manager.ts:1152-1188](/Users/tsandberg/.cache/pi-source/v0.99.2/packages/coding-agent/src/core/session-manager.ts)). A managed launcher should always provide a persistent exact ID; missing file path should therefore fail closed. Create the roster row at the first accepted user turn, not at `session_start`.

## Remaining uncertainty

Pi has no transactional coupling between its JSONL append and the recorder's SQLite commit: extension `message_end` runs immediately before SessionManager persistence. A power loss in that narrow interval can leave the DB excerpt/unarchive one message ahead of JSONL, while reversing the order would leave it behind. Recovery should treat Pi's transcript as authoritative if this mismatch is detected, or accept the tiny window; eliminating it requires an upstream post-persistence extension event. The lifecycle classification itself is unaffected because `agent_start`/`agent_settled` bracket the whole run.
