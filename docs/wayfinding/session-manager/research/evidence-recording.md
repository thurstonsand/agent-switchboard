# Evidence recording

## Decisions

### TUI-only scenarios

Use Charmbracelet VHS tapes as executable evidence specifications, rendered to MP4 for review (and optionally GIF for a README-sized preview). VHS drives a PTY by typing text and special keys, waiting for screen/line regexes, and controlling terminal dimensions; it is therefore independent of the application's Bubble Tea major version and can drive the future Bubble Tea v2 binary as a black box. Prefer `Wait+Screen`/`Wait+Line` over fixed sleeps around state transitions. VHS supports GIF, MP4, WebM, and PNG-frame-directory outputs, including multiple outputs from one tape ([VHS README, command reference](https://github.com/charmbracelet/vhs#vhs-command-reference)).

VHS is obtainable on this host but is not presently installed. A non-mutating `brew info vhs` probe on the work Mac reported bottled `vhs` 0.12.1, depending on `ffmpeg` and `ttyd`; `brew info ffmpeg` reported bottled 9.0.2, also not installed. The configured work proxy is `https://go-proxy.crwd.dev`, and `GO111MODULE=on go list -m -versions github.com/charmbracelet/vhs@latest` successfully returned releases through v0.12.1. Installing only the Go module is insufficient because VHS requires `ttyd` and `ffmpeg` on `PATH` ([VHS installation documentation](https://github.com/charmbracelet/vhs#installation)). Declare the Homebrew formula through this repository's software capability before evidence production; do not ad-hoc install it.

A tape should launch an isolated fixture database and dedicated test socket, set rows/columns, exercise navigation and actions with keys, and assert recognizable post-action text before proceeding. This covers roster rendering, sections, filters, archive/undo, and similar terminal-only scenarios. It does not prove Ghostty dispatch or focus behavior because VHS renders its own virtual terminal.

### Ghostty-integrated scenarios

Use macOS's built-in `/usr/sbin/screencapture` for the real-Ghostty videos. It is present now, while `ffmpeg` is absent. The local macOS command's own usage output documents `-v` for video, `-V<seconds>` for a fixed duration, `-R<x,y,w,h>` for a screen rectangle, `-l<windowid>` for a window ID, `-D<display>`, and `-k` for visible clicks (local probe: `/usr/sbin/screencapture -h`, which deliberately returned usage without starting capture). The conservative production command is a timed, fixed rectangle around a manually positioned Ghostty window, for example `screencapture -v -V20 -R100,100,1200,800 artifact.mov`. A permission-safe spike must still confirm whether this macOS build accepts `-v` combined with `-l`; the usage advertises both flags but does not explicitly promise that combination. If it does, window-ID capture is preferable to coordinate cropping.

Do not use ffmpeg/AVFoundation as the baseline. It is not installed, and FFmpeg's AVFoundation input selects a capture device by enumerated index/name rather than a Ghostty window; its documented `capture_screen` option captures the screen, not an individual application window ([FFmpeg AVFoundation input documentation](https://ffmpeg.org/ffmpeg-devices.html#avfoundation)). It would add a dependency without solving window targeting.

Screen capture requires prior user/administrator coordination. Apple directs users to **System Settings > Privacy & Security > Screen & System Audio Recording** to enable an application, after which it may need to quit and reopen ([Apple, Control access to screen and system audio recording](https://support.apple.com/guide/mac-help/control-access-to-screen-and-system-audio-recording-mchld6aa7d23/mac)). On managed Macs, Apple's PPPC payload is installed through device management and is more restrictive when multiple payloads exist; notably, its Screen recording setting can deny capture ([Apple Platform Deployment, PPPC payload](https://support.apple.com/guide/deployment/privacy-preferences-policy-control-payload-settings-dep38df53c2a/web)). IT must ensure policy does not deny the relevant executable, then the user must grant the permission Apple presents. Which process macOS will attribute for this exact shell invocation (Ghostty versus `screencapture`) remains uncertain and must be observed during an approved setup session. This research did not invoke capture or a preflight API. A read-only query of the user's TCC database was itself denied, so current authorization is unknown.

Drive the scenario without synthetic macOS keystrokes:

- For terminal text entry, target the viewer's TTY with `gty input --tty /dev/ttysNNN --submit --wait 'text'`. GhosttyKit joins the arguments, addresses the requested TTY, optionally submits Enter, and optionally waits for acknowledgement (`~/code/personal/ghosttykit/cli/gty/commands_input.go:11-29`; protocol fields at `~/code/personal/ghosttykit/sdk/go/protocol/protocol.go:401-423`).
- For deterministic keys inside a tmux-hosted TUI, use `tmux -L sessions send-keys -t <target> ...`; tmux defines `send-keys` as sending keys or literal characters to a target pane ([tmux(1), `send-keys`](https://man.openbsd.org/tmux.1#send-keys)).
- Reject AppleScript/System Events as the normal driver: it introduces separate Apple Events or Accessibility approval surfaces; Apple's PPPC reference lists AppleEvents, Accessibility, and Post Event separately from Screen recording ([Apple PPPC payload settings](https://support.apple.com/guide/deployment/privacy-preferences-policy-control-payload-settings-dep38df53c2a/web)). It also tests UI automation rather than the product's supported interfaces.

Record dispatch by sending the action into the real TUI, then visibly show the new viewer. Record focus-existing-viewer by moving focus elsewhere, invoking open again, and showing focus returning without a second viewer. `gty --wait` acknowledges delivery, not completed application state, so scripts should gate subsequent actions on product-visible state or tmux `capture-pane`, not arbitrary sleep.

Fixed-rectangle capture is reproducible only after the Ghostty window has been placed at the prescribed coordinates. Automating window placement without another control permission was not established from a primary source, so manual placement is an explicit precondition rather than a hidden claim of determinism.

### Reboot-survival scenario

Do not falsify a boot ID. macOS's boot identity cannot honestly be changed without booting, and changing a database value would test a fixture rather than survival. Instead, label the recording **simulated process loss** and exercise the reboot-relevant boundary:

1. Launch isolated managed sessions against a copied/fixture SQLite store and transcript directory: one Idle and one deliberately held mid-turn.
2. Record their durable state, then run `tmux -L <isolated-test-socket> kill-server`. `kill-server` kills the tmux server and its clients; tmux otherwise keeps programs running after clients detach, which is why killing the server is the relevant stronger boundary ([tmux getting started, detaching and servers](https://github.com/tmux/tmux/wiki/Getting-Started); [`kill-server`](https://man.openbsd.org/tmux.1#kill-server)).
3. Ensure no fixture Pi process remains, restart `sessions` as a fresh process, and show both rows restored from durable state: the formerly Idle session is Dormant, while the mid-turn session is Interrupted.
4. Open or `R`-revive each and show transcript continuity. Do not auto-continue the interrupted turn.

The fixture must use a different tmux socket and database from the live `sessions` deployment; otherwise the test would destroy real work. This demonstrates survival of owned-process loss and fresh-process reconstruction, which are the application-controlled parts of reboot handling. It does **not** prove an actual macOS reboot, launch environment, filesystem availability after login, or a genuine kernel boot-ID transition. The video and review notes must say so. If acceptance requires those properties, only a separately scheduled real reboot can supply that evidence.

### Artifact storage and delivery

Commit the small textual inputs—the VHS tapes, fixture setup, scenario manifest, and exact recording commands—alongside the eventual implementation. Keep rendered videos out of ordinary Git and Git LFS. LFS still stores pointer files in Git and consumes separate storage/bandwidth quotas ([GitHub, About Git Large File Storage](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage)); it is unnecessary for review outputs that can be regenerated.

During production, render into an ignored local evidence directory (or `/tmp`), name each file by scenario and implementation revision, and create a checksum manifest. Hand the MP4s to Thurston by attaching them to the implementation PR/issue: GitHub accepts `.mp4`, `.mov`, and `.webm` attachments in issues and pull requests, with 10 MB per video on the free plan and 100 MB on paid plans ([GitHub, Attaching files](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files)). If a video exceeds the applicable limit or evidence must remain downloadable after the PR, publish a tagged GitHub release containing the videos and manifest; releases are designed to carry binary assets and each file must be under 2 GiB ([GitHub, About releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)). Do not use Actions artifacts as the sole record because they expire according to repository retention ([GitHub, Downloading workflow artifacts](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)).

Uncertainty: this repository's eventual forge/visibility and paid-plan attachment limit were not established by the ticket. The durable fallback is a release asset; the immediate handoff can also be the local absolute paths plus SHA-256 manifest when Thurston is on this machine.
